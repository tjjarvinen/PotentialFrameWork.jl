# CPU ACE force-merge benchmark and neighbor rebuild reuse

Use the local VS Code checkout of PotentialFrameWork.jl. Run Julia, tests, and benchmarks on the local Ryzen 9 9950X workstation. Read the applicable AGENTS.md files. Record the starting revision and working-tree state, then preserve local changes, the reference fixtures, and the results from PR #20.

This handoff has two deliverables. First, add a controlled benchmark for inline versus worker-dispatched force merging. Second, implement reusable neighbor and chunk preparation and measure its effect on rebuild cost. Keep the existing production merge policy for this benchmark campaign. The subsequent review will decide whether to adopt inline merging. A trajectory-driven rebuild policy, equivariant readout threading and pullbacks, and MACE implementation are later work.

The prior one-group reuse diagnostics at 16 cores put merge-phase wall time at 10.8–11.3 ms and the sum of the force-merge worker intervals at 0.21–0.29 ms. The outer timer also includes dispatch and completion and the serial energy and virial reduction. At eight cores, fresh evaluations were about 37 ms slower than evaluations with topology reuse, and the separate environment and chunk-layout probes allocated about 50 and 47 MB per call. Treat those values as historical reference points. Collect a matched baseline on the starting revision.

## 1. Benchmark the force merge

1. Extend the current harness with a benchmark-selectable inline merge. Use the current `ChunkWave.routes` and `merge_scatter_run!`. Run the routes on the coordinating task after site workers complete each wave. Preserve the existing order of additions to each destination, keep the same energy and virial reduction, and finish consuming a wave before reusing its scatter slots. Keep site evaluation threaded in both variants. Use a private or benchmark-only selector unless an existing internal configuration already supports the choice.
2. Compare the existing worker-dispatched merge with the inline variant on the same implementation, with the same prepared graph, chunk layout, waves, inputs, and output boundary. Use the existing 3,456-atom Ti and Ti–Al–V fixtures at eight and 16 physical cores, one logical group, Float64, SIMD width four, site batch size one, and topology reuse. Use warmed public E/F/V calls with owning outputs. Confirm each frame is actually evaluated and both variants agree on E/F/V on all replay frames. Compare the alternatives before the rebuild changes or against an identical layout and source revision.
3. Keep end-to-end timing runs free of diagnostic instrumentation. In separate diagnostic runs, record the dispatch interval, enqueue-to-worker-entry delay where measurable, worker body time, completion receipt and wait, and serial energy/virial reduction. Record phase wall times and worker intervals separately. Dispatch, wakeups, worker execution, and completion can overlap. Include the inline phase with the same timing boundary. Repeat the diagnostic runs to show spread, since the prior 16-core data were isolated observations.
4. Retain the raw timings and summarize the difference in end-to-end latency and merge-phase wall time at eight and 16 cores. Call out cases where the difference falls within run-to-run spread. Keep the default on the existing merge path for this handoff.

## 2. Reuse storage when rebuilding neighbors and workgroups

### Measure the baseline first

Use the existing fresh versus position-refresh replay, starting with the two large fixtures above. For fresh calls, record full public latency, allocations and GC time. Capture the existing `FullEnvironment.timings` and add scoped probes where needed for coordinate/species extraction, cell preparation, directed graph traversal and snapshot materialization, species packing and footprints, coloring, cell permutation, chunk layout, and `chunk_thread_plan` route construction. Route planning is not included in the existing `form_numa_workers` probe. Label probes that are nested or run independently. Compare end-to-end timings separately.

### Implement reusable preparation through the normal ACE entry point

- Add a reusable neighbor preparation interface in `NeighbourList` using `prepare_neighbors!` and a reusable neighbor object or explicit build workspace, as required by the existing concrete types and ownership. Keep the allocating entry point usable. Retain capacity for the cell workspace, permutations, and packed neighbor buffers where practical. Have the generic chunk preparation reuse the same cell preparation for graph construction and cell-order metadata when they can share it safely. The exported snapshot query still owns its data. The internal chunk path can avoid copying or materializing a query result it does not consume if the baseline supports that change and the same traversal preserves exact directed image labels.
- Add `form_numa_workers!` to refill existing `ChunkWorkgroups` for the new neighbor generation, with a documented allocating fallback where types or incompatible settings require it. Retain atom-mark scratch and destination and run-vector capacity, and reuse compatible group and chunk storage. Replace the per-site sort and growing `union` with reusable integer scratch. Deduplicate as sites enter a chunk, preserve single-site capacity errors and chunk splitting, and sort the completed destination list once before computing contiguous runs. Existing `SiteChunk` values can keep their wrapper design and reuse owned vectors when a new center range requires a replacement wrapper.
- Make fresh chunk-based `AC.calculate` calls with a retained `ACEEvaluationState` exercise those reusable paths. Reuse the existing worker pool and compatible scatter storage. Invalidate routes and rebuild them for the new generation even when atom counts, chunk counts, or worker counts match. Retained feature fields and results tied to the old layout must be invalidated. Previously returned owning outputs must stay valid.
- Measure schedule construction before changing it. If building site coloring on fresh chunk calls is material, make internal preparation build it for consumers that need it. Keep colored/legacy consumers correct, including a change of executor on an existing state. Start with ordinary state-owned scratch. Consider Bumper.jl only if profiling still identifies significant task-local, nonescaping temporary allocations. Adding it is optional. Persistent arrays and anything borrowed by another task need storage with an appropriate lifetime.
- Document the actual mutating signatures, what the caller owns, and when views become stale. A fresh build can reuse storage even when the graph changes. Position refresh on an already valid graph keeps that topology and its routes. Treat a failed in-place rebuild as invalid until a clean fresh rebuild succeeds, unless the implementation can preserve the previous complete generation. Guard against mutation during an active pass and publish a consistent generation on success.

### Verify and measure

- Through the normal scalar ACE calculator path, compare reusable fresh rebuilds against the allocating baseline across successive geometries, including a changed graph with unchanged counts. Check directed neighbor/image parity, original-order E/F/V with existing tolerances, capacity-driven chunk splitting, and an already returned owning output after later rebuilds. Exercise serial chunks and threaded chunks. Cover the relevant existing tests for periodic crossings, repeated/self images, cell and species changes, graph shrink and growth, failed rebuild and retry, and the colored path. Add focused regressions where existing coverage does not exercise the new mutation or invalidation behavior.
- Rerun the same rebuild campaign on the updated implementation. Use the same frames, precision, worker counts, and rebuild schedule for the before/after comparison. Keep the existing graph-preserving position refresh as a separate reference. Include a correctness check on frames that force graph changes. Report public latency, allocation bytes, GC time, and measured rebuild substages for Ti and Ti–Al–V. Report the starting and updated revisions or source and harness hashes, plus the actual scope of any optional snapshot or coloring changes. Save any trajectory-based decision about rebuild frequency for the follow-up.

## Run protocol and handoff

Use one Julia compute thread per selected physical core and BLAS=1. Record effective CPU masks, the CPU-to-core and L3/CCD mapping, Julia and dependency versions, model and workload settings, and governor or frequency settings if available. Verify the masks locally before running. Keep placement identical within each paired comparison. Warm up all variants, run them sequentially, alternate their order across repetitions where practical, and collect at least ten warmed observations per primary comparison when the benchmark budget permits. Retain individual observations and report sample counts and spread.

Deliver the benchmark and rebuild changes through the local source tree, focused validation, exact runnable commands, new raw results alongside the historical results, and a short report under `benchmark/cpu_chunks/`. Report merge latency by policy, before/after rebuild latency and allocations, and any unresolved attribution or correctness checks. This phase is complete when the production entry point exercises reusable rebuilding, existing behavior passes the applicable regression checks, and both benchmark comparisons are reproducible.
